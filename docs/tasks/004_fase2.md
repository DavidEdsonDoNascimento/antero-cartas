Quero iniciar agora a:

**FASE 2 — Persistência e infraestrutura mínima**

As Fases 1, 1.1 e 1.2 já foram concluídas e validadas.

Atualmente o produto já possui:

* landing page;
* fluxo de criação em quatro etapas;
* preview em tempo real;
* autosave local;
* até 6 fotografias;
* carrossel de imagens;
* temas;
* contador de tempo;
* pesquisa de música pela YouTube Data API;
* opção de colar link manual do YouTube;

* modo demonstrativo;
* páginas legais;
* analytics stub;
* testes das funcionalidades de música;
* experiência mobile-first.

Agora quero substituir as limitações locais por uma infraestrutura mínima que permita criar, persistir, publicar e abrir uma carta em qualquer dispositivo.

Não implemente pagamento real nesta fase.

6. ACESSO AO RASCUNHO SEM LOGIN
===============================

O produto continua sem autenticação.

Implemente um mecanismo seguro e simples para o comprador editar o próprio rascunho.

Sugestão:

* ao criar o rascunho, gerar um token aleatório;
* armazenar somente o hash do token no banco;
* guardar o token original apenas no navegador;
* enviar o token nas requisições de edição;
* comparar o hash no servidor;
* nunca utilizar apenas o `cartId` como autorização.

Estrutura possível:

```text
cartId
editToken
```

Armazenar no navegador apenas o mínimo necessário para retomar o rascunho.

Use um token criptograficamente seguro.

Não use JWT sem necessidade.

Não colocar o token na URL pública da carta.

Documente as limitações deste modelo sem login.

7. MIGRAÇÃO DO RASCUNHO LOCAL
=============================

Hoje existem dados no `localStorage`.

Implemente uma migração gradual:

1. verificar se existe um rascunho local antigo;
2. criar um rascunho no backend;
3. enviar os dados textuais;
4. preservar dados de música;
5. tentar enviar as fotos locais, quando possível;
6. armazenar `cartId` e `editToken`;
7. confirmar que o backend recebeu os dados;
8. somente então remover ou marcar o rascunho antigo como migrado.

A migração deve:

* ser idempotente;
* não criar várias cartas ao atualizar a página;
* não apagar o rascunho antigo antes da confirmação;
* não quebrar caso uma imagem local não possa ser migrada;
* informar discretamente quando fotos precisarem ser selecionadas novamente.

Depois da migração, o backend deve ser a fonte principal.

O `localStorage` pode continuar sendo usado como cache ou recuperação temporária, mas não como fonte definitiva.

22. PUBLICAÇÃO DA CARTA
=======================

Uma carta só pode ficar pública quando:

* tiver pedido pago;
* tiver título;
* tiver mensagem;
* tiver remetente;
* tiver destinatário;
* possuir plano válido.

Ao publicar:

* gerar slug seguro;
* utilizar pelo menos 128 bits de entropia;
* garantir unicidade;
* não reutilizar `cartId` diretamente;
* definir `publishedAt`;
* calcular `expiresAt`;
* alterar status para `PUBLISHED`.

Para plano limitado:

```text
expiresAt = paidAt + PLAN_LIMITED_DURATION_DAYS
```

Para plano permanente:

```text
expiresAt = null
```

Não interpretar “para sempre” como garantia absoluta de existência infinita. Use a linguagem comercial configurada e os termos do produto.
