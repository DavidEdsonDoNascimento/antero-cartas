* segura;

# 2. Decisões já tomadas

## 2.1 Supabase

O plano gratuito atualmente já possui dois projetos ativos:

* `antero-atendimentos`;
* `antero-cartas`.

Não existe disponibilidade para criar um terceiro projeto remoto.

A arquitetura definida para esta fase será:

```text
Desenvolvimento
└── Supabase local com CLI e Docker
    ├── PostgreSQL local
    ├── Supabase Storage local
    ├── migrations versionadas
    ├── seed e dados fictícios
    └── testes locais e de integração

Produção
└── Projeto remoto atual antero-cartas
    ├── PostgreSQL remoto
    ├── Supabase Storage remoto
    ├── dados reais
    └── acesso da aplicação publicada
```

Portanto:

* não crie um terceiro projeto Supabase;
* não utilize o projeto `antero-atendimentos`;
* não misture dados dos dois produtos;
* não faça upgrade de plano;
* não crie organização paga;
* não contrate serviços pagos;
* não utilize o projeto remoto como ambiente normal de desenvolvimento;
* aceite conscientemente a ausência de staging remoto nesta versão.

## 2.2 Domínio

O domínio público definido será:

```text
https://cartas.anterosistemas.com.br
```

O domínio principal `anterosistemas.com.br` já pertence à empresa.

Não compre um domínio separado.

## 2.3 Hospedagem

A aplicação será preparada para publicação na Vercel.

Não crie `vercel.json` sem necessidade real. Use a configuração padrão da plataforma sempre que ela for suficiente.

## 2.4 Orçamento

Não contrate nenhum serviço pago.

Integrações como Sentry e analytics só podem utilizar plano gratuito ou permanecer preparadas aguardando credenciais.

# 6. Etapa 2 — Supabase local

## 6.1 Inicialização

Configure o desenvolvimento com Supabase CLI e Docker.

O ambiente local deve oferecer:

* PostgreSQL;
* APIs locais do Supabase;
* Supabase Storage;
* bucket utilizado pelas fotos;
* migrations;
* seed local;
* suporte aos testes de integração.

Verifique primeiro se já existe configuração parcial.

Não duplique arquivos corretos.

Prepare e documente comandos equivalentes a:

```bash
supabase init
supabase start
supabase status
supabase stop
supabase db reset
```

Adapte os comandos ao projeto real.

Não execute comandos destrutivos contra o projeto remoto.

## 6.2 Migrations

Garanta que o ambiente local possa ser recriado do zero.

Depois do reset local, devem existir corretamente:

* `Cart`;
* `CartMedia`;
* `Order`;
* `EmailDelivery`;
* enums;
* índices;
* constraints;
* relacionamentos;
* índices únicos de idempotência.

Preserve o Prisma como camada de acesso aos dados.

Não use `prisma db push` como substituto das migrations versionadas.

Não execute `prisma migrate dev` no banco remoto.

Se as migrations do Prisma e o fluxo do Supabase CLI precisarem de coordenação, escolha uma única fonte de verdade para o schema e documente claramente essa decisão. Não mantenha dois históricos de migration independentes e divergentes.

## 6.3 Seed

Crie ou ajuste um seed exclusivamente local, somente se necessário.

Ele pode conter:

* carta fictícia;
* pedido fictício;
* mídias fictícias;
* dados necessários aos testes.

Não inclua:

* dados pessoais reais;
* CPF real;
* telefone real;
* e-mail real;
* segredos;
* credenciais;
* URLs privadas.

O seed não pode ser executado automaticamente em produção.

## 6.4 Storage local

O desenvolvimento deve utilizar Supabase Storage local para reproduzir o comportamento de produção.

Garanta que:

* o bucket local seja criado de forma idempotente;
* uploads locais nunca sejam enviados ao projeto remoto;
* as URLs locais sejam válidas;
* os testes não dependam da internet;
* o provider seja selecionado por variável de ambiente.

Preserve o provider de filesystem já existente quando ele ainda for útil para testes isolados. Não o remova apenas por limpeza.

## 6.5 Proteção contra produção

Implemente uma proteção simples contra o uso acidental do banco remoto durante o desenvolvimento.

A proteção deve impedir ou alertar claramente quando:

```text
NODE_ENV=development
```

estiver combinado com uma configuração identificada como produção.

Evite depender apenas de nome de projeto ou comparação frágil de URL.

Prefira uma variável explícita, por exemplo:

```env
APP_ENV=local
```

e uma confirmação adicional para operações administrativas de produção, caso seja necessária.

A proteção deve:

* não expor credenciais;
* não quebrar testes;
* não bloquear produção legítima;
* não criar um sistema complexo de configuração.

## 6.6 Arquivos de ambiente

Corrija o `.gitignore` para permitir o versionamento de `.env.example`.

Exemplo:

```gitignore
.env*
!.env.example
```

Crie um único `.env.example` claro, salvo justificativa para mais de um arquivo.

Organize por categorias:

* aplicação;
* banco;
* Supabase;
* Storage;
* YouTube;
* pagamento mock;
* e-mail mock;
* Sentry;
* analytics;
* flags de desenvolvimento.

Não inclua valores reais de:

* senha;
* token;
* service role;
* URL privada;
* chave de API;
* DSN privado.

O ambiente local real deve permanecer em `.env.local` ignorado pelo Git.

# 7. Etapa 3 — Preparação do projeto remoto

O projeto remoto atual `antero-cartas` será o ambiente de produção.

## 7.1 Operações destrutivas

Não apague nem altere dados remotos de forma destrutiva sem minha autorização explícita.

Antes de qualquer limpeza:

1. liste o que foi encontrado;
2. identifique por que parece ser dado de teste;
3. prepare o backup;
4. apresente o comando ou script;
5. aguarde autorização.

Nunca use condições genéricas que possam futuramente remover dados reais.

## 7.2 Backup

Documente como preservar:

* schema;
* migrations;
* dados;
* arquivos do bucket;
* configuração do bucket;
* variáveis necessárias.

Registre as limitações de backup do plano gratuito.

Não afirme que existe backup completo enquanto ele não tiver sido efetivamente criado e verificado.

## 7.3 Limpeza

Prepare, mas não execute sem autorização, um procedimento seguro para remover:

* cartas de smoke test;
* pedidos fictícios;
* registros com domínio `@seed.local`;
* arquivos reconhecidamente fictícios;
* outros registros de desenvolvimento identificados durante a auditoria.

A limpeza deve ser revisável e baseada em identificadores explícitos.

## 7.4 Banco remoto

Garanta que:

* runtime utilize a conexão apropriada;
* migration utilize a conexão apropriada;
* pooler continue compatível;
* nenhuma credencial seja hardcoded;
* produção utilize `prisma migrate deploy`;
* nenhum comando de desenvolvimento seja executado contra produção.

Avalie se `DIRECT_URL` continua necessária com a configuração atual do Prisma e Supabase. Preserve-a se houver necessidade real.

## 7.5 Storage remoto

Valide o `SupabaseStorageProvider` existente.

Garanta que:

* o script de criação do bucket seja idempotente;
* ele não cause erro quando o bucket já existir;
* a service role permaneça somente no servidor;
* a service role não apareça no bundle;
* os caminhos dos arquivos sejam não enumeráveis;
* não exista listagem pública desnecessária;
* as URLs finais funcionem;
* a configuração seja documentada.

Não altere a arquitetura de upload preventivamente.

## 7.6 Ambientes da Vercel

Separe as variáveis de:

* Development;
* Preview;
* Production.

Como não existe staging remoto, Preview não pode escrever no banco de produção.

Use a solução mais simples e segura, preferencialmente:

* não disponibilizar credenciais de produção no ambiente Preview;
* bloquear operações de escrita em Preview;
* permitir que Preview valide apenas build e páginas que não dependem do backend.

Não crie outro banco.

Não utilize `antero-atendimentos`.

Documente o comportamento e as limitações do Preview.

# 8. Etapa 4 — Deploy, domínio e performance

## 8.1 Deploy na Vercel

Prepare o projeto para deploy com:

* instalação das dependências;
* `prisma generate`;
* migrations de produção;
* build do Next.js.

Avalie a forma mais segura de executar:

```bash
prisma migrate deploy
```

Considere:

* builds concorrentes;
* deployments de Preview;
* migration executada no ambiente errado;
* falha no meio da migration;
* rollback.

Não presuma que colocar migrations diretamente no comando de build é automaticamente a melhor opção.

Explique a decisão adotada.

Preview nunca pode executar migration contra produção.

## 8.2 Domínio

O domínio será:

```text
https://cartas.anterosistemas.com.br
```

Siga esta ordem:

1. publique inicialmente na URL da Vercel;
2. adicione o domínio ao projeto da Vercel;
3. obtenha no painel da Vercel o registro DNS necessário;
4. informe-me:

   * tipo;
   * host/nome;
   * destino;
   * TTL, quando aplicável;
5. aguarde minha alteração manual no DNS;
6. valide a propagação;
7. valide o certificado HTTPS;
8. configure as URLs públicas;
9. faça novo deploy;
10. valide links, QR Code, sitemap, canonical e metadata.

Não altere o DNS automaticamente.

Não presuma onde o DNS está hospedado. Caso isso não possa ser determinado pelo repositório ou pela configuração disponível, apenas me peça para informar o provedor no momento do checkpoint.

Não considere o domínio validado até conseguir verificar o acesso HTTPS.

## 8.3 URLs públicas

Revise o uso de:

* `NEXT_PUBLIC_APP_URL`;
* `NEXT_PUBLIC_SITE_URL`;
* canonical;
* metadata;
* sitemap;
* link da carta;
* QR Code;
* compartilhamento por WhatsApp.

Caso as duas variáveis tenham a mesma responsabilidade, consolide-as somente se isso puder ser feito com baixo risco.

Caso ambas sejam mantidas, documente a diferença.

Em produção, rejeite:

* `localhost`;
* domínio placeholder;
* protocolo inválido;
* valor vazio;
* URL malformada.

A validação não pode quebrar desenvolvimento local ou testes.

## 8.4 QR Code

Crie ou ajuste testes para garantir:

* URL local em desenvolvimento;
* URL pública em produção;
* ausência de `localhost` em produção;
* slug correto;
* ausência de barra duplicada;
* ausência de token de edição;
* ausência de dados pessoais no link.

## 8.5 Publicação para smoke test

Não habilite `mock-confirm` publicamente em produção.

Não crie uma rota temporária ou backdoor de publicação.

Para validar uma carta pública e o QR Code antes da Fase 3, utilize somente uma destas alternativas:

1. uma carta de teste que já esteja publicada no banco remoto; ou
2. um script local, não exposto como endpoint e executado manualmente com autorização explícita; ou
3. um procedimento SQL manual, documentado e autorizado.

Qualquer método deve:

* ser explícito;
* não ficar acessível pela internet;
* não permitir publicação gratuita por um visitante;
* não permanecer como mecanismo permanente;
* ser registrado no handoff.

Apresente a opção recomendada antes de executá-la.

## 8.6 Experiência de entrada

Confirme que:

* o clique em “Criar minha cartinha” apresenta interface imediatamente;
* não existe tela branca com apenas “Carregando...”;
* o skeleton existente funciona;
* criação de sessão não bloqueia a renderização;
* uma nova carta não carrega silenciosamente a carta anterior;
* retomada de rascunho continua sendo uma decisão explícita.

Não refatore novamente o que já estiver correto.

## 8.7 Autosave

Confirme que:

* digitação não é bloqueada;
* troca de etapa não espera salvamento sem necessidade;
* respostas obsoletas continuam sendo descartadas;
* falha remota não apaga o conteúdo local;
* feedback de salvamento não deixa a experiência visualmente lenta.

## 8.8 Upload e preview

Confirme que:

* preview local aparece imediatamente;
* compressão ocorre antes do envio;
* upload acontece em segundo plano;
* existe indicação discreta de progresso;
* erro é exibido claramente;
* foto com falha não é considerada concluída;
* checkout não avança enquanto houver upload pendente ou falho.

## 8.9 Limite de fotos

O limite atual é seis fotos.

Não reduza automaticamente para três.

Teste:

* uma foto;
* três fotos;
* seis fotos.

Somente recomende redução após evidência de prejuízo relevante à experiência.

Não altere a regra comercial sem minha autorização.

## 8.10 Testes de upload

Prepare testes com arquivos representativos:

* aproximadamente 5 MB;
* aproximadamente 10 MB;
* aproximadamente 15 MB;
* foto real de Android;
* foto real de iPhone, quando disponível;
* uma, três e seis fotos;
* Wi-Fi;
* rede móvel, quando possível.

O Claude pode executar testes automatizados e locais.

Testes físicos em Android, iPhone e rede móvel que dependam dos meus dispositivos devem ser entregues como checklist manual, com campos para eu informar os resultados.

Registre:

* tamanho original;
* resolução original;
* tamanho comprimido;
* resolução final;
* tempo até o preview;
* tempo de compressão;
* tempo de upload;
* status HTTP;
* mensagem de erro;
* tamanho salvo no Storage.

Não invente resultados de testes que não puder executar.

Se houver falha, tente primeiro:

* compressão mais eficiente;
* resolução máxima menor;
* limite explícito antes do envio;
* melhor mensagem de erro;
* controle de concorrência.

Somente proponha upload direto ou URL assinada quando as soluções simples não resolverem.

Não implemente a mudança arquitetural sem apresentar antes:

* evidência;
* alternativas;
* impacto;
* risco;
* esforço;
* recomendação.

## 8.11 Plano gratuito

Mantenha o Supabase no plano gratuito.

Não implemente mecanismos artificiais para evitar pausa.

Documente:

* possibilidade de pausa;
* ausência de SLA;
* limites de banco;
* limites de Storage;
* limitações de backup;
* sinais que indicarão a necessidade futura de upgrade.

# 9. Etapa 5 — Operação básica

## 9.1 Sentry

Implemente monitoramento básico client-side e server-side utilizando plano gratuito.

A integração deve funcionar de maneira opcional. Sem DSN, a aplicação continua funcionando.

Capture principalmente:

* falha de criação de rascunho;
* erro de persistência;
* erro de upload;
* erro de banco;
* erro de criação de pedido;
* erro de publicação;
* exceções de API;
* falha da carta pública.

Não envie:

* token de edição;
* conteúdo integral da carta;
* título da carta;
* CPF;
* telefone;
* e-mail completo;
* cookie sensível;
* autorização;
* service role;
* segredo;
* URL contendo token.

Implemente sanitização.

Caso a criação da conta ou obtenção do DSN dependa de mim:

1. implemente a integração;
2. documente a variável;
3. informe o passo manual;
4. continue os demais itens;
5. não considere o envio efetivamente validado até receber o DSN e realizar o teste.

Não deixe uma rota pública que gere erro deliberadamente.

## 9.2 Analytics

Os eventos existentes devem ser preservados.

Não crie um sistema próprio.

Use uma solução simples, gratuita e preferencialmente cookieless.

Registre no mínimo:

* `landing_viewed`;
* `create_started`;
* avanço nas etapas;
* `checkout_started`;
* `payment_confirmed` somente nos ambientes em que a confirmação mock for autorizada.

Não envie:

* nome;
* e-mail;
* telefone;
* CPF;
* conteúdo da carta;
* título;
* token;
* slug privado;
* URL sensível.

A aplicação deve funcionar quando analytics estiver desabilitado.

Caso a ativação dependa de painel externo ou credencial, implemente o adapter e documente o checkpoint manual.

Não implementar:

* testes A/B;
* dashboard próprio;
* UTM avançada;
* recuperação de carrinho;
* automação de marketing.

## 9.3 SEO e compartilhamento

Implemente somente:

* `sitemap.ts`;
* `/sitemap.xml`;
* revisão de `robots.ts`;
* canonical;
* metadata;
* imagem Open Graph;
* Twitter/X card;
* configuração para compartilhamento no WhatsApp.

A imagem deve seguir a identidade visual existente.

Não criar:

* blog;
* páginas sazonais;
* landing pages adicionais;
* estratégia extensa de conteúdo.

## 9.4 Headers de segurança

Configure:

* `Content-Security-Policy`;
* `X-Content-Type-Options`;
* proteção contra framing;
* `Referrer-Policy`;
* `Permissions-Policy`;
* HSTS somente em HTTPS.

Antes da CSP, levante todos os domínios realmente usados por:

* Supabase;
* YouTube;
* imagens;
* Sentry;
* analytics;
* aplicação.

Não utilize `*` indiscriminadamente.

Não quebre:

* player de música;
* fotos;
* upload;
* Sentry;
* analytics;
* QR Code;
* carta pública.

## 9.5 Mocks

Produção deve usar:

```env
ALLOW_MOCK_PAYMENT_CONFIRMATION=false
DEV_EMAILS_ENABLED=false
PAYMENT_MODE=mock
EMAIL_MODE=mock
```

Enquanto a Fase 3 não existir:

* a aplicação pode criar pedido pendente;
* produção não pode confirmar pagamento por rota mock;
* produção não pode publicar gratuitamente por rota de desenvolvimento;
* `/api/dev/*` deve estar bloqueado;
* mensagens não devem expor detalhes internos.

Desenvolvimento local deve continuar permitindo o fluxo mock.

Crie ou preserve testes para esses guards.
