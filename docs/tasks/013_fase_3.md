# Task 013 — Fase 3: Venda Real

Retomada autônoma pedida em 2026-07-29, depois do encerramento técnico da
Fase 2.5 (`docs/0008_Handoff_Fase2_5_Final.md`) e da aprovação das validações
manuais (checklist físico e evento de Sentry).

## Objetivo

Transformar o produto num MVP comercial capaz de: receber pagamento real
(Pix e cartão via Mercado Pago), confirmar por webhook confiável, publicar a
carta somente após confirmação válida, entregar o link por e-mail real
(Resend), tratar todos os estados de pagamento, impedir publicação gratuita,
detectar/registrar falhas, e permitir suporte manual nas primeiras vendas.

Fim da fase = **produto apto para a primeira venda real.**

## Fornecedores

Mercado Pago (pagamento) e Resend (e-mail transacional) — definidos pelo
usuário, não escolhidos por mim. Ambos atrás das interfaces `PaymentProvider`
e `EmailProvider` já existentes (preservadas, estendidas quando necessário,
nunca substituídas).

## Princípio de segurança financeira

Sandbox/teste primeiro. Não processar cobrança real nem ativar credenciais de
produção sem autorização explícita. Não alterar os mocks de produção
(`PAYMENT_MODE`, `EMAIL_MODE`) até: integração sandbox funcionando, webhook
testado e com assinatura validada, eventos duplicados cobertos, publicação
idempotente, e-mail validado, e smoke test completo aprovado.

## Escopo detalhado

Ver seções 8–17 do pedido original (pagamento, webhook, estados, frontend,
e-mail, DNS, segurança, observabilidade, analytics, testes) — resumo:

- `RealPaymentProvider` para Mercado Pago: Pix + cartão, preço/plano/moeda
  sempre calculados no servidor, nunca confiar no cliente.
- Webhook dedicado (`/api/webhooks/mercadopago`), validação de assinatura
  oficial, idempotência, tolerância a duplicado/fora de ordem/pagamento
  desconhecido. É a **única** fonte de verdade para aprovação — nunca o
  retorno do navegador, query string, redirecionamento ou polling do front.
- Estados mapeados explicitamente (Mercado Pago → interno), sem strings do
  fornecedor espalhadas pelo domínio.
- Frontend objetivo para Pix (QR, copia-e-cola, validade, polling limitado) e
  cartão (Payment Brick, sem dado sensível passando pelo servidor).
- `RealEmailProvider` (Resend) reusando o outbox `EmailDelivery` existente;
  sem fila/Redis — reprocessamento simples e controlado.
- DNS de e-mail (SPF/DKIM/DMARC) preparado, DNS não alterado automaticamente.
- Segurança: credenciais só no servidor, nada sensível em Sentry/analytics/
  logs, rate limit básico, validação Zod, assinatura de webhook, idempotência,
  proteção contra adulteração de preço.
- Testes obrigatórios cobrindo preço/assinatura/idempotência/estados/e-mail/
  polling, com fakes e fixtures — sem depender da API real para a suíte toda.

## Fora do escopo

Painel admin completo, Redis, Kafka/RabbitMQ, cupons, assinatura recorrente,
WhatsApp Cloud API, recuperação de carrinho, IA, temas premium, edição
pós-compra, i18n, refatoração ampla, migração de infraestrutura.

## Checkpoints humanos previstos

Conta/autenticação Mercado Pago; credenciais sandbox/produção; criação da
aplicação no Mercado Pago; configuração manual do webhook no painel;
conta/autenticação Resend; verificação de domínio de e-mail (DNS); alteração
manual de DNS; definição de remetente; dados legais/comerciais; autorização
para cobrança real; autorização para alterar flags de produção; teste com
cartão/Pix/dinheiro real; qualquer operação destrutiva ou migration
destrutiva; decisão comercial não definida.

Nenhum desses bloqueia o trabalho de código, testes, documentação ou
migrations aditivas — só a validação sandbox ponta a ponta e a ativação real.
